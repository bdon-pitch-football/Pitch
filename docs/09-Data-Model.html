Foundations — the data model

The choices that can never be retrofitted, designed before a line of code. Built on register decisions D-10, D-17–D-26, D-48–D-51, and extended on 27 August by D-101 to D-144. Read §⓪ first — it carries six objects this document was written before, and where it disagrees with anything below it, §⓪ wins. There is no build date: the gate is doc 14 green, not a calendar (D-131).

⓪ The 27 August objects — read this before anything below it

This document was written on 25 August and six objects joined the model on 27 August. Where this section and anything later in the file disagree, this section wins and the later text is stale. Register v3.8 (D-01 – D-144).

One deletion first, because it is the sharpest error in this file. §② below describes a “Registrant Record — trial-applicant row… ships post-launch”. That object is gone, and both halves of the sentence are now wrong: it ships in Phase 1 (D-108, D-130), and the words applicant, application, declined, rejected, unsuccessful do not exist in this product for any actor on any surface (D-108 extending D-85). It is replaced by registration, below. A player registers interest in a club. A trial is a tag on that registration, never a separate object.

Owned by the club · read by the club

registration

A player’s standing interest in a club. Not an application, not a queue, and no verdict is ever owed. Fields: player_id · club_id · squad_target · positions[] · trial_tag (nullable — a trial is a tag, not a parent object) · note · club_status · created_at · disclosed_by · policy_version.

Three invariants, each with a doc 14 row:
• club_status has exactly three values and none of them is a verdict, and it never reaches the player (doc 14 §N10). declined, rejected and unsuccessful cannot be written.
• Revocation empties note in the same transaction that withdraws the row (D-128, §N7). The note is child-authored content sitting on our row, not behind the token — killing the link never touched it, and “nothing readable survives” is only true if this is atomic.
• No route serialises more than one registration (D-122, §N12). There is no export, no CSV, no download, not behind a flag.

Decisions: D-108, D-122, D-128, D-130
The gate · not a badge

club_state & verification_call

The single most important column in the schema. club_state is unclaimed · claimed · verified · suspended. No fact about a person under 18 reaches a club that is not verified (D-126).

verified is written only by an operator action carrying operator, called_at and number_source. Not a webhook, not a payment, not a claim, not a domain match, not a backfill, not a migration. Doc 14 §M4 asserts no automated path exists — it is the one row that, if it fails, means a card payment is all that stands between an adult and a child’s details.

The verification_call table is doc 27’s thirteen log fields, built as written: club_id · called_at · operator · number_called · number_source · answered_by · club_confirmed · person_confirmed · incorporated · authority_confirmed · outcome · notes · policy_version. number_source is NOT NULL — a blank invalidates the call, because ringing the number on the claim form verifies nothing.

Held, not rejected: registrations arriving for an unverified club are held. The club sees a count and nothing else, and held rows are indistinguishable by enumeration from an empty club (§J61).

Decisions: D-126, D-137, D-139, D-142 · doc 27 is the schema
Owned by the player · gated by the guardian

The approved / pending version pair

An under-16 record now has two versions (D-119). The public page renders the approved one; the child sees their own pending edit and a waiting state.

Four properties, and the second is the one that gets built wrong:
• A club holding a link keeps seeing the last approved page while an edit is pending.
• The page never blanks and nothing is taken down during pending. An implementation that unpublishes while awaiting approval has quietly punished the child for editing.
• No timeout publishes a pending version (§R7). Silence keeps the approved page live, indefinitely.
• The guardian reviews what changed, not the whole page again.

At 16–17 and 18+ the original live-page behaviour is unchanged: one version, edited directly.

Decisions: D-119, D-103 · doc 14 §R
Owned by the club → answered by the guardian

invitation

The only route from a club to a family, and it never leaves Pitch (D-117). Fields: club_id · registration_id · body · created_at · read_at (private to the family) · reply_id.

The outbound notification is a bare wake — no child name, no club name, no message, no action inside it (doc 15 §24). A forwarded notification leaks nothing and a phone face-up on a bench shows nothing.

Silence produces no state a club can see (D-138): no seen, no pending, no counter, no timestamp, and no difference between ignored and never-arrived. Any visible state turns silence into a signal, and a signal invites a second approach.

The club never receives a phone number or an email address, before or after. The guardian replies field by field; nothing is shared by default. If they choose to hand over their own contact details, that is an adult’s choice about their own data and the conversation leaves Pitch — that escape hatch is what makes this work without building messaging.

No club→player message exists outside this path, asserted by route enumeration rather than a permission check (§P11).

Decisions: D-117, D-138 · doc 14 §P
Owned by the club · never touches a child

subscription

Stripe hosted Checkout and the hosted Customer Portal only — never embedded card fields, which is what keeps us at PCI SAQ-A (D-112). Fields on the club record: plan · status · current_period_end · grace_until · stripe_customer_id.

status is written only by webhook. The permission check reads that flag and nothing else.

Payment failure suspends; it never deletes (D-135). Fourteen days of grace, then the register is suspended — registrations hidden from the club, not destroyed. Deletion runs only on cancellation, thirty days later. A family’s child is never deleted because a club’s card expired, and families are never told a club’s payment failed. The suspended state reuses the same computed permission as unverified.

Two hard walls: no billing surface is reachable from any player, family or under-18 view — including portal links and Stripe receipt emails (D-82, D-88) — and Stripe never receives child data (§O10). Payment must never be able to set club_state.

Decisions: D-112, D-135, D-136, D-137 · doc 14 §O
Guardian-gated · irreversible once out

share_card_approval

A player picks a card; the guardian sees the exact image before it can leave (D-101 as amended, 27 Aug).

No image is generated or given a URL before approval — which is why no approval email carries a preview, since a preview is a generated image on a public URL sitting in an inbox before anyone agreed to anything. Byte-identical to what was approved, asserted by hash (§Q2).

A minor’s card carries no URL, QR code or handle that resolves to their record. If it points anywhere it points at pitchfootball.com.au, which is a front door and not a child.

Once approved it cannot be recalled (§Q8) — and the product says so plainly rather than implying a control we do not have.

① One separation everything hangs on

A person, their profile, and their record are three different objects. The person is the human (one account, even wearing two hats — coach and parent is common). The profile is the public face per role — the CVs. The record is the development history — player-owned, portable (D-10). Keeping them apart is what makes the locked architecture buildable: a U16 profile can be invisible while the record keeps growing; a coach-parent is one login; a club change moves the record without touching the club's own data.

② The ten objects

Owned by the person

Person / Account

One per human. Roles are hats, not accounts. DOB drives the age state machine. A child's account comes into existence only by verified guardian approval (D-17) — through either door: parent-created, or child-initiated as a pending invitation holding first name + DOB + parent contact only, auto-purged after 14 days if unapproved. The CV gets built after approval, never before.

Decisions: D-17, D-49
Owned by the person

Profile (per role)

PlayerProfile, CoachProfile, ClubProfile — two CVs and a claimed club page (D-74). Each carries a visibility state computed from age band + guardian settings + D-22. Share links are tokenised: revocable and regenerable at any time; U16 links default to 90-day expiry (guardian adjustable, one-tap renew with reminder) and the guardian can pause the profile (D-53).

Decisions: D-18, D-22
Owned by the player

Development Record

The core object (D-10). Assessments, stats, achievements, highlight links. Travels whole between clubs (D-48). Never paywalled to its owner (D-31). Every stat and entry carries a provenance tag — self-reported · coach-verified · official-import (D-62) — a first-class field from day one, so future Dribl/Veo partnerships slot in as a third tier of truth with no migration, and the UI always says honestly where a number came from.

Amended 25 Aug — the atomic unit is a typed entry (D-71). The record holds generic entries with a type discriminator (attendance · participation · effort observation · milestone · coach note · competency observation), not a competency-scores table with other things bolted on — so effort and participation are never second-class. Stats are rows, not columns (D-70): a player_stat table keyed by stat_key, with the position-to-stat-set catalogue held in TypeScript rather than Postgres. Max four tiles; nulls omitted, never rendered as zero. No negative numbers on a minor's public CV, ever (D-67).

Decisions: D-10, D-31, D-48, D-67, D-70, D-71
Dual-attributed

Assessment

Authored by a verified coach as criterion-referenced competency bands (Introduced → Developing → Consolidating → Owns it), organised by the Four Corners — never numeric ratings (D-60). Each row references a Competency belonging to either the Pitch spine or a ClubFramework layer; spine rows are cross-club comparable, club rows travel as attributed history. Carries context markers (relative age within band). 48h edit window → immutable; corrections supersede visibly (D-50). Attribution + read-access persist for the author (D-48).

Amended 25 Aug (D-71): the atomic unit is the AssessmentEntry — one player, one competency, one band, one author, one moment. "An assessment", as a parent reads it and as D-50 governs it, is a derived grouping over entries by player and block. This is shape-agnostic: player-major entry, competency-major sweeps, mixed entry and single-tap corrections all work with no migration between them. Two rules that carry the promise: entries reference competencies by (competency_id, framework_version), never by name; and there is no unique constraint on (record_id, competency_id, block_id) — append-only supersession is what leaves room for a later TD moderation entry.

Decisions: D-11, D-12, D-50, D-71
The legal spine

Guardianship Link

Guardian ↔ child. ≤2 guardians, equal visibility, either approves, both notified, most-restrictive-wins (D-51). Carries consent state; auto-expires at 18 (D-49) with re-grant by the adult player.

Decisions: D-17, D-49, D-51
Append-only

Consent & Audit Log

Every approval, revocation, share, outside-contact attempt and age transition, logged immutably. Powers the parent's "you see everything" promise and the D-26 deletion cascade.

Club

Entity with verified status (manual verification in v1 — the gate before any minor data flows to it), admins, and the ClubProfile CV.

The club walls

Membership

Person ↔ club/squad with role and season. A squad is a lens, not a container — records stay player-owned; squad membership grants access through it. Season-scoped (U14 Girls 2027). U16 squad invites route to the guardian for approval. Coach assignment (verified coaches only, several per squad) is what grants assess + read rights. Defines "inside the club" for contact rules (D-19).

Amended 25 Aug (D-93) — the role list, and the split that matters. role is: player · coach · technical_director · team_manager · club_admin · guardian. Club administrator and Technical Director are different powers: an administrator runs the club page, squads, memberships and notices and holds no development-record access; the TD holds club-wide development access. TD is granted by the club and confirmed at club verification, never self-declared. A person holding both roles gets the union, computed at read time.

Amended 25 Aug. Competition gender lives here, on the squad — never on a child's Person record (D-68). Squad carries competition_gender and age_group; "U15 Girls" is a fact about a competition, not an identity attribute on a minor (D-25). Age groups, tiers and gendered pathways are lookup tables, never enums (D-73). And the wall: because Membership is what defines "inside the club", the new experience_entry object (D-72) is deliberately kept out of it — see below.

Decisions: D-19, D-21, D-25, D-68, D-73

The trust layer

Verification Status

On adults: club-attested WWCC state + club affiliation (D-28 as narrowed by D-98 — the engine keys off a boolean attestation, never a check number) — a permission gate, not a badge: it unlocks assessing and 16–17 discovery (D-22). ③ The age state machine (D-49)

Birthdays are state transitions, not support tickets. Guardians are notified 30 days before each transition. Everything is automatic, logged, and reversible only where a switch is defined.

Under 16

  • Parent-created, parent-approved (D-17)
  • Visible via parent-controlled link; in no search (D-18)
  • No feed, likes, follows, DMs (D-21)
  • Contact: own club via squad; outside → guardian + child together (D-19)
→
16th birthday · countdown moment (D-20)

16 – 17

  • Network unlocks: follow, connect, feed
  • Discoverable to verified clubs & coaches only (D-22); guardian holds off-switch
  • Contact still routed to guardian + player together (D-20)
  • Guardian visibility continues
→
18th birthday · independence (D-49)

18 +

  • Fully open: public profile, open search, direct contact
  • Guardian visibility auto-expires; player can re-grant by choice
  • Premium eligible (D-33)

Club visibility, precisely: the technical director and squad-assigned verified coaches see the full development records of players currently at their club — a club administrator never does, by any route (D-93) — including the history a new signing brings with them (the record travels whole, D-48; consented by the guardian at joining). When a player leaves, the club drops to aggregates and each authoring coach keeps read-access to what they wrote. No sideways visibility: parents see their own child only; coaches see their own squads only.
The engine's one rule of construction: permissions are computed from objects (age band + guardianship state + membership + verification), never stored as flags on a user. That's what makes birthdays automatic, "verified" a real gate, and the whole matrix testable — we can assert every cell in code before launch.

⑤ The 25 August schema delta

Seven changes taken on 25 Aug, all of them cheap now and expensive-to-catastrophic later. Ranked honestly — rows 1–3 are the argument, the rest is housekeeping.

New object — experience_entry ("other football"), and it has zero permission surface (D-72). School football, futsal, representative and NTC programs, tournaments. Fields: kind (school · futsal · representative · ntc_academy · tournament · other), org_name as free text with no foreign key to club — deliberately, competition, season label, dates, positions, notes; provenance always self-reported at launch. Hard invariant with a test that is not optional: experience_entry never participates in the permission engine and grants read access to nobody, ever. The tempting shortcut — a nullable club_id on Membership plus a free-text org name — is a hole into a child's record, because unverified user input would then touch the object that defines "inside the club". No taxonomy: a type chip and free text, never a dropdown of school competitions.
Changed — player profile positions (D-69). Two scalar columns (primary_position, secondary_position) are replaced by positions[], ordered, maximum three, TypeScript-validated. Goalkeeper is a pickable position. There is no position_status / "finding" state — position is optional and its absence renders neutrally. position_group (GK/DEF/MID/FWD/UNSET) is derived at read time from positions[0], never stored — same discipline as permissions.
New — player_stat, and this is the irreversible one (D-70). Keyed by (record_id, season, stat_key, source_experience_id) with provenance (D-62). The stat catalogue lives in TypeScript, so adding "saves" or "minutes" later is a code change with zero migration. If Apps/Goals/Assists ship as columns instead, then from launch day every real family writes into a shape that cannot express "clean sheets", and the fix becomes a live-data migration across minors' records, under a public page, in December. Catalogue honesty limit: appearances, goals, assists, clean sheets, minutes only — self-reported tackles, interceptions, duels and saves are excluded, because nobody counts them and everybody would estimate upward (D-11).
New — verification_challenges (D-80). channel · hashed token · sent_at · verified_at · attempt count · expiry, read by the permission function. Supabase Auth is used for session only. It models one identity with one primary channel and cannot express "this adult proved an email address and, separately, a phone number, and only then does a child's record unlock". Do not use phone-OTP sign-in as the second factor — it collides with the email identity and costs days in account-linking fights.
New — the consent funnel event spine (D-78). Append-only, fixed vocabulary, one row per state transition, with email and SMS provider delivery webhooks writing into the same table. Without delivery telemetry, "the parent ignored us" and "Gmail spam-foldered us" are indistinguishable from inside our own logs.
Anticipated, on empty tables — free to change, specified for clarity not urgency. competency (+ position_scope: all · gk · outfield; band_descriptors as structured JSON; unique on code + framework_version) · assessment_entry (+ entry_type: coach · td_sample · moderation; supersedes_entry_id; context_marker carrying relative age in band, D-61/D-84) · assessment_block · assessment_session (optional header with mode: player_major · competency_major, so we learn empirically which flow coaches use) · match_appearance (D-66 — family sees season totals, staff see per-match, never on the public CV) · growth_note (guardian-entered height and date only, coach-invisible, no classification — D-84).
Irreversibility ranking — differentiated, not uniform. 1. player_stat rows not columns — catastrophic: live minors' data, migrated under a public page, in December. 2. assessment_entry as the atomic unit — catastrophic in December, free today, because D-50's immutability and supersession get rebuilt on whatever the unit turns out to be. 3. experience_entry outside Membership — catastrophic if done wrong (a permission leak), free if done right. 4. positions[] vs two scalars — trivial SQL. 5. competition_gender on squad — a small backfill. 6. Everything on empty tables — free either way. The schema is not on the cut line at all: features bend, the shape of the data does not.
Added 25 Aug — three decisions with schema consequences that arrived after this document. D-96 (age assurance): Person carries a dob_locked flag (no upward amendment without guardian or verified-club confirmation), a signup_hold state for the age-contradiction hold, and a guardian contact is mandatory on a fresh 16–17 signup — an account without one is incomplete, not merely unverified, because D-22 and D-20 are unbuildable without it. D-88 (clips): every highlight carries added_at and added_as_minor — the 18th-birthday transition grandfathers clips added as a minor permanently, and cannot be implemented without the marker. D-91 (share): the U16 row of the permission matrix is child requests, guardian dispatches — a share-request object, not "guardian only".
